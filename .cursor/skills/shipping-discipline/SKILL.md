# Shipping discipline

Two questions govern every change: **(1) Am I building it the way this product
builds things?** and **(2) Is this something that should be merged, or something
that only helps me locally?** Getting (2) wrong is how a teammate pulls the
branch and their environment breaks, or how local scaffolding leaks into
production. This skill keeps those two answers crisp.

## The local-vs-PR boundary (the most important thing)

A PR branch is a shared, user-visible artifact on the path to merge. Anything in
it runs on every teammate's machine and in production. So the branch should
contain **only the real change** — the feature, fix, or refactor — and nothing
that exists purely to make *your* machine work.

**Belongs in the PR** (the actual work):
- Product code: components, styles, logic, types, tests for the change.
- Anything a reviewer would expect to see for the feature/fix.

**NEVER goes in the PR** (local-only scaffolding — keep it uncommitted or gitignored):
- `.env.local` and any secret/credential/token values.
- Database seeds and fixtures used to unlock gated features locally (plan/subscription rows, feature-flag rows, "connected" state, super-admin flags, etc.).
- Local-only env wildcards or bypasses (e.g. `SOMEFLAG_IDS=*`, `DEV_LOGIN_*` tokens).
- Dev-login / auth-bypass shims (routes, vite proxies, passthroughs) — even when guarded, they don't belong in product code unless the team owns that pattern.
- Local dev tools added as dependencies (e.g. `agentation`) and their mount points.
- Mock/preview routes and fixture data (`*Mock*`, `LOCAL_PREVIEW*`, demo seed objects).
- **Temporary debug instrumentation** — `console.log`, `window.__debug`, on-screen diagnostic labels, forced-visible elements, etc. Remove every last one before committing. If you added it to diagnose, you added it to delete.

If you genuinely need a compatibility shim, fallback, or staged-migration seam,
do not add it silently — call it out loudly to the user and let them decide.

**Before any commit or push, run this sweep** (catches the leaks above):

```bash
# staged/working changes you're about to ship
git diff --stat HEAD

# the usual leak patterns — each hit needs a conscious "is this meant to ship?"
git grep -nE 'console\.(log|debug)|__debug|LOCAL-ONLY|dev-login|agentation|TEMP|FIXME|XXX' -- '*.ts' '*.tsx'
```

A useful tell: search your own diff for the marker comments you (or another
agent) left, like `// LOCAL-ONLY ...`. Those lines are a checklist of things to
keep out of the PR. If a line is local-only, it should be uncommitted, in a
gitignored file, or behind a dev gate that tree-shakes out of prod — not staged.

## GitHub PR text — write it lowercase

A personal convention: for any PR pushed on the user's behalf, write the **PR
title and the whole description in lowercase**, including the section headers
inside the body. No Title Case, no Capitalized Headings, no capitalizing words
for emphasis. This applies to every text field you author on GitHub for their
PRs — title, body prose, header/section lines, and bullet labels.

- Do: `fix slack nav icon sizing to match the heroicons`
- Don't: `Fix Slack Nav Icon Sizing To Match The Heroicons`
- Leave code, file paths, identifiers, and acronyms / proper nouns exactly as
  written (`SlackSolidIcon`, `coderabbit-ui`, `CI`, `viewBox`). Markdown
  structure (`##`, lists, links) stays — only the words get lowercased.

**No AI attribution.** Do NOT add the `Co-Authored-By: Claude ...` trailer to
commit messages, and do NOT add the `🤖 Generated with Claude Code` line (or any
equivalent "generated by" / co-author note) to PR bodies or commits. The user
does not want their PRs or git history attributed to an AI assistant — leave it
out of every commit message and PR description, even though the default tooling
suggests adding it.

## Build with carrot-ui — always

Product UI uses the `@coderabbitai/carrot-ui` design system. Reach for its
primitives and tokens before hand-rolling anything; a raw `<div>` with custom
borders is almost always a carrot component you haven't used yet. Consistency
here is what makes the product feel like one product, and it's what reviewers
look for.

- **Primitives over raw markup**: `Button`, `Card`, `Avatar`, `Select`,
  `SettingsCard`, `Form.*`, `Popover`, `Table`, etc. If you're drawing a bordered
  container by hand, use `Card`/`SettingsCard` instead.
- **Design tokens over literal colors**: `bg-cui-base-1` / `bg-cui-base-2`,
  `text-cui-primary` / `-secondary` / `-tertiary`, `border-cui-neutral`,
  `ring-cui-neutral`, `text-cui-danger`, `bg-cui-success`. Don't introduce raw
  hex or generic Tailwind grays for product surfaces.
- **Icons are heroicons solid** (`@heroicons/react/16/solid` for inline UI,
  `/20/solid` for sidebar/header, `/24/solid` for prominent contexts). Size with
  `className="size-4"`, not `size={N}`. Never ship a stray text glyph (e.g. a
  literal `"v"` as a dropdown caret) or a one-off SVG when a heroicon exists. If
  migrating, replace lucide/custom icons with heroicons.
- **Button variants** are carrot's documented visual-style names:
  `primary | outline | secondary | transparent | danger | danger-light` (see
  DESIGN.md §6.3 / the `carrot-ui-principles` skill — these are all valid; don't
  "fix" `outline`/`transparent` away). Pick by emphasis: the main action →
  `primary`; secondary/cancel actions → `secondary` or `outline`; low-emphasis /
  icon-style → `transparent`; destructive → `danger` / `danger-light`.
- **className overrides work** — carrot uses `tailwind-merge`, so passing
  `className` to a primitive reliably overrides its defaults (radius, padding,
  bg). Use that instead of forking a component.
- **Match the existing structural patterns** rather than inventing spacing. e.g.
  `SettingsCard` renders `card → inner wrapper → bg-cui-base-2 block`, and rows
  inside get `px-4 py-3`. When you add content to such a card, pad it the same
  way the neighbors are padded; copy a sibling's structure instead of guessing.
- **Respect the redesign's conventions**: breadcrumbs instead of duplicated
  in-page titles; no stray hairline divider rules unless the design system uses
  them. When unsure, find a working example on an adjacent surface and mirror it.

When in doubt about whether something is "carrot enough," trace it: are the
colors `cui-*` tokens? Is the container a carrot primitive? Is the icon a
heroicon? If any answer is no, fix that before calling it done.

## Refactor what you touched (before the PR)

Once the change works, do one cleanup pass — scoped to the code you added or
edited, not the whole file or neighbouring features. The goal is to leave the
touched surface a little better than you found it without widening the diff or
risking unrelated behaviour.

What this pass looks for, in the lines you changed:
- **Extract complex inline logic.** A 70-line `useEffect`, a hand-rolled control
  with its own state and handlers, or a big inline event handler reads better as
  a named hook (`useXyz`) or a small component. Pull it into its own file next
  to its siblings.
- **De-duplicate within scope.** Repeated literals, repeated option objects, or
  the same `setValue(..., { shouldDirty, shouldValidate })` shape can become a
  local helper — but only the call sites you touched; don't rewrite the file's
  existing style around them.
- **Name things.** Inline closures, magic numbers, and `data-` string flags read
  clearer as named consts/handlers.

Hard constraints on the pass:
- **Behaviour- and pixel-preserving.** If the user approved how it looks or
  acts, the refactor must not change either — extraction moves code verbatim, it
  doesn't redesign. Re-verify in the running app afterwards, the same way you
  verified the feature.
- **Stay inside the blast radius.** "Refactor the areas we touched" means the
  files/blocks this change introduced or modified — not a tour through adjacent
  code that happened to be nearby. Untouched code stays untouched.
- **Respect surface-local precedent.** If a surface already deviates from the
  global rules for a reason (e.g. a receipt-themed billing panel that uses raw
  hex to match Figma exactly), don't "fix" that during the pass — you'd be
  reverting an intentional, approved choice.

## Setting up local dev (and keeping it local)

Local tooling makes iteration fast — set it up freely, just keep it out of the
PR (see the boundary above). Gate everything behind a dev check so it can never
ship even if a file is accidentally committed.

- **agentation** (visual feedback tool for agents, by Benji Taylor): install as
  a dev dependency and mount it dev-gated so production builds tree-shake it:
  ```bash
  pnpm add -D agentation   # or npm/yarn/bun
  ```
  ```tsx
  // root layout — dev-only, lazy, tree-shaken from prod builds
  const Agentation = import.meta.env.DEV
    ? lazy(() => import("agentation").then(m => ({ default: m.Agentation })))
    : undefined
  // ...render: {Agentation ? <Suspense fallback={null}><Agentation /></Suspense> : null}
  ```
  Click an element, annotate it, copy the structured markdown (selectors,
  element path, source line) and hand it to your agent so it edits the exact
  code. This is a *local aid* — it and its dependency entry stay out of the PR.
- **Mock/preview routes** for designing surfaces without real data: gate with
  `import.meta.env.DEV` so they don't exist in production. Useful for reviewing
  UI states, but the fixtures are local-only.
- **Local backend / dev-login / seeds**: fine to run locally to unlock gated
  features for testing, but every one of these is on the NEVER-push list.

When you change how local dev works in a way that future-you (or another agent)
needs to reproduce, record the recipe in a memory note — not in the codebase.

## Dos and don'ts

| Do | Don't |
| --- | --- |
| Build UI from carrot-ui primitives + `cui-*` tokens | Hand-roll bordered divs or use raw hex/generic grays |
| Use heroicons; carrot's documented Button variants | Ship text-glyph icons or one-off SVGs when a heroicon exists |
| Gate local tooling behind `import.meta.env.DEV` | Leave a dev tool or mock reachable in prod |
| Keep `.env.local`, seeds, wildcards, dev-login uncommitted | Stage local env, secrets, or auth bypasses |
| Delete every debug line before committing | "Leave it, I'll clean it later" |
| `git diff --stat HEAD` + grep for leak markers pre-push | Push without reading your own diff |
| Verify the real change in the running app | Assume it works because it compiled |
| Write commit/PR descriptions that say what changed and why | Terse, context-free messages |
| Write GitHub PR titles + descriptions (incl. headers) in lowercase | Title Case or Capitalized PR headings |
| Refactor the code you touched, behaviour-preserving, then re-verify | Refactor untouched/adjacent code or redesign approved UI during cleanup |

The throughline: **fast and messy locally, clean and honest in the PR.** Iterate
however you like on your machine; merge only the real change.
